# Feedback: Content-Based False Positives — `strings.Contains` Without Context

> **RESOLVED** — Commits `ca7ed14` (header-only scanning), `6816645` (sqlc filename narrowing), and `91cc17c` (config-aware phase 1.5). All three root causes addressed: header-only scanning eliminates import/string/code false positives; sqlc filename patterns narrowed to `.sql.go` suffix only; config-aware detection classifies fixed filenames (models.go, db.go, etc.) as sqlc-generated iff they live in a declared output dir. See `docs/status/2026-08-10_13-05_config-aware-sqlc-detection.md` for details.

## Summary

gogenfilter's two-phase detection misclassifies hand-written Go files as generated
because content checks use `strings.Contains` on the entire file body without verifying
that the matched string is an actual generation comment per the
[Go generated-code spec](https://go.dev/s/generatedcode). This produces a ~2.8% false-positive
rate on non-test files in a real-world corpus of 158 Go projects. The false positives fall
into three root causes, each with a concrete fix.

## Consumer: go-humanize-linter

[go-humanize-linter](https://github.com/LarsArtmann/go-humanize-linter) is an AST-based
linter that uses gogenfilter's `IsGeneratedFile` wrapper to skip generated files. During
the T2 real-world validation sweep (2026-08-10, 158 Go projects), I compared every `.go`
file in the corpus against the files the linter actually scanned.

**Headline numbers:**

| Metric | Count |
| ------ | ----- |
| Non-test `.go` files skipped by gogenfilter | 1,469 |
| Correctly skipped (real generated files) | 1,428 (97.2%) |
| **Incorrectly skipped (false positives)** | **41 (2.8%)** |

The 41 false positives break down into three root causes, detailed below.

---

## Root Cause 1: sqlc filename match returns without content verification

### The bug

The sqlc detector has a filename pattern table (`detection.go:227`):

```go
var sqlcFilenamePatterns = []string{"models.go", "querier.go", "query.sql.go", "batch.go"}
```

Phase 1 (`getFilenameBasedReasonWithTrace`, `detection.go:595`) checks filenames against
this list. If the filename matches, it returns `ReasonSQLC` **immediately** — the content
checker never runs:

```go
// detection.go:601-607
for i := range detectors {
    d := &detectors[i]
    if _, enabled := options[d.option]; enabled {
        if d.matchFilename != nil && d.matchFilename(filename) {
            return d.reason, fmt.Sprintf("detected as %s via filename pattern", d.option)
        }
    }
}
```

### The problem

`batch.go` is a common filename for batch-processing logic that has nothing to do with sqlc.
Any file named `batch.go` is silently classified as sqlc-generated, with zero content
verification.

### Evidence — 12+ hand-written `batch.go` files flagged as sqlc

Every file below was confirmed as hand-written (no `// Code generated by sqlc` header, no
sqlc API calls, first line is `package <name>`):

| File | Actual content |
| ---- | -------------- |
| `auto-deduplicate/pkg/prompts/batch.go` | AI batch prompt builder |
| `go-cqrs-lite/event/batch.go` | Event batching logic |
| `go-cqrs-lite/storage/view/batch.go` | View batch processing |
| `invoices/internal/gobl/batch.go` | GOBL batch invoice creation |
| `PapDashboard/internal/api/batch.go` | API batch handler |
| `vision-review-agent/pkg/vision/batch.go` | Vision batch processor |
| `nsfw-classifier/cmd/nsfw-classify/batch.go` | Classification batch runner |
| `projects-management-automation/pma-daemon/batch.go` | Daemon batch processor |
| `project-discovery-sdk/enrichment/repoinfo/github/batch.go` | GitHub API batch enrichment |

Additionally, `models.go` and `querier.go` in non-sqlc database directories
(~20 files across the corpus) are flagged without content verification.

### Fix

**Phase 1 filename match should require phase 2 content confirmation for sqlc.** The sqlc
detector should use AND semantics (filename matches AND content contains sqlc markers),
not OR semantics (filename matches OR content matches):

```go
// Option A: Make filename match a gate, not a shortcut return
// getFilenameBasedReasonWithTrace should return "tentative" and require content check
// before confirming ReasonSQLC.

// Option B: Remove ambiguous patterns from sqlcFilenamePatterns
// Keep ".sql.go" suffix (specific enough), drop bare "batch.go", "models.go", "querier.go"
// These are too common as hand-written filenames.
var sqlcFilenamePatterns = []string{"query.sql.go"} // drop "models.go", "querier.go", "batch.go"
```

## Root Cause 2: `strings.Contains` on full file body — the oapi-codegen case

### The bug

The oapi-codegen detector (`detection.go:71`) has `matchFilename: nil` — no filename gate.
Its content checker (`IsOapiGenerated`, `detection.go:392`) is:

```go
func IsOapiGenerated(_, content string) bool {
    return strings.Contains(content, oapiCodegenMarker) // "oapi-codegen"
}
```

This searches the **entire file body** — imports, comments, string literals, variable names.

### The problem

Any file that mentions "oapi-codegen" anywhere is classified as generated. This catches
files that **import** `oapi-codegen/runtime/types` (legitimate dependency, not generated),
files that **document** oapi-codegen support, and even gogenfilter's **own source code**.

### Evidence — 6+ categories of false positives

| File | Trigger string | Context |
| ---- | -------------- | ------- |
| `gogenfilter/doc.go:5` | `"oapi-codegen"` in a doc comment listing supported generators | Documentation |
| `gogenfilter/types.go:38,39,111,112` | `"oapi-codegen"` as a `FilterOption`/`FilterReason` constant value | Source code |
| `golangci-lint-auto-configure/.../scanner.go:201,234,239` | `"oapi-codegen"` in a switch case and exclusion pattern descriptions | Source code |
| `go-finding/.../generated_filter.go:31` | `"oapi-codegen": gogenfilter.FilterOapi` as a map entry | Source code |
| `art-dupl/config/config.go:105` | `"oapi-codegen"` in a comment discussing which generators the config supports | Comment |
| `branching-flow/pkg/core/config.go:98` | `"oapi-codegen"` in a comment listing covered generators | Comment |
| `branching-flow/pkg/fs/fs.go:85` | `"oapi-codegen"` in a comment describing content detection | Comment |
| `CV/internal/helper/psychological_impact.go:12` | `"github.com/oapi-codegen/runtime/types"` — a **legitimate import** | Import |
| `CV/schema/psychological_impact.go:3` | Same import | Import |
| `CV/schema/type_aliases.go:5` | `// Generated from OpenAPI spec via oapi-codegen.` | Comment (but not a `// Code generated` header) |

### Fix

**Use AST-aware detection or at minimum check comment position.** The Go generated-code
spec requires the `// Code generated by` comment to appear **before the `package` clause**.
A `strings.Contains` on the full body violates this.

Options:
1. **AST-aware**: Parse the file, check only comments before `package` declaration (best, but
   adds `go/parser` dependency).
2. **Pre-package-clause scan**: Only search the portion of content before `package` appears.
   Lightweight, no AST dependency.
3. **Import-path-aware**: For oapi-codegen specifically, exclude files where the only match
   is an import path (`"github.com/oapi-codegen/..."`), not a generation comment.

## Root Cause 3: sqlc code-pattern markers match source code that discusses sqlc

### The bug

The sqlc content checker (`hasSQLCContent`, `detection.go:323`) has a third detection path
beyond the generation comment:

```go
// detection.go:291-298
var sqlcCodePatternMarkers = []string{
    "sqlc.Arg",
    "sqlc.NamedArg",
    "sqlc.Literal",
    "sqlc.SliceArg",
    "sqlc.Narg",
    ".query(ctx",
}

func hasSQLCCodePatterns(content string) bool {
    return anyMatch(content, sqlcCodePatternMarkers, strings.Contains)
}
```

### The problem

Any file containing the string `"sqlc.Arg"` anywhere — including in a `[]string` slice that
defines the patterns — is classified as sqlc-generated. **gogenfilter's own source code
triggers this.**

### Evidence

| File | Trigger | Context |
| ---- | ------- | ------- |
| `gogenfilter/detection.go:292-296` | `"sqlc.Arg"`, `"sqlc.NamedArg"`, etc. as string literals in `sqlcCodePatternMarkers` | The detection patterns themselves |
| `gogenfilter/testhelpers/constants.go:25` | `"// Code generated by sqlc. DO NOT EDIT."` as a test constant | Test fixture |

The linter's generated-file detector (`go-finding/cmd/go-finding/generated_filter.go`) is
also flagged as oapi-codegen (see Root Cause 2), and `gogenfilter/detection.go` is flagged
as sqlc. **gogenfilter classifies its own source code as generated.**

### Fix

The `sqlcCodePatternMarkers` check should verify that these appear as actual function calls
in Go source (e.g., `sqlc.Arg(`), not as string literals. AST-aware detection would solve
this, or at minimum a more specific pattern like `"sqlc.Arg("` with the opening paren.

## Impact on go-humanize-linter

These false positives mean go-humanize-linter silently skips hand-written files. In the
158-project corpus, 41 hand-written files were skipped. None of them contained
humanize-reimplementable patterns, so the impact was low for this specific consumer.
However:

1. The false positives are **non-obvious** — a developer whose `batch.go` file is skipped
   has no way to know without running gogenfilter separately and checking the reason.
2. The false-positive rate compounds with corpus size — a 10,000-file codebase would see
   ~280 hand-written files silently skipped.
3. **gogenfilter cannot detect its own source files** — `go test ./...` inside the
   gogenfilter repo would classify `detection.go`, `doc.go`, `types.go`, and
   `testhelpers/constants.go` as generated.

## Summary of Proposed Fixes

| Root cause | Fix | Effort |
| ---------- | --- | ------ |
| `batch.go`/`models.go`/`querier.go` filename-only match | Require content confirmation for ambiguous filenames (AND instead of OR) | Low — change `getFilenameBasedReasonWithTrace` to return "tentative" for sqlc and require phase 2 |
| `strings.Contains` on full file body (oapi-codegen) | Scan only content before `package` clause, or use AST-aware detection | Medium — add a `prePackageContent(content)` helper or integrate `go/parser` |
| `sqlcCodePatternMarkers` matching source code strings | Require `sqlc.Arg(` (with paren) or AST-aware call detection | Low — add `(` suffix to patterns |

## Reproduction

```bash
# Build go-humanize-linter
cd ~/projects/go-humanize-linter
nix run .#build

# Check any batch.go file
go-humanize-linter --list-files ~/projects/go-cqrs-lite/event/
# batch.go will NOT appear in the list (silently skipped as "sqlc-generated")

# Verify with DetectReason directly
cat > /tmp/repro.go << 'EOF'
package main

import (
    "fmt"
    "github.com/LarsArtmann/gogenfilter/v3"
)

func main() {
    // batch.go with no sqlc content
    content := "package event\n\nfunc ProcessBatch() {}\n"
    reason := gogenfilter.DetectReason("batch.go", content, gogenfilter.FilterAll)
    fmt.Printf("batch.go → %s\n", reason) // prints "sqlc" (WRONG)

    // File that mentions oapi-codegen in a comment
    content2 := "package config\n\n// Supports oapi-codegen detection\nfunc Load() {}\n"
    reason2 := gogenfilter.DetectReason("config.go", content2, gogenfilter.FilterAll)
    fmt.Printf("config.go → %s\n", reason2) // prints "oapi-codegen" (WRONG)
}
EOF
```
