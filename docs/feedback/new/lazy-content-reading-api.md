# Feedback: Lazy Content Reading API for Two-Phase Detection

## Summary

gogenfilter's two-phase detection (filename then content) already reads file content lazily internally, but no public API returns that content to the caller. Consumers that need the content for post-detection checks are forced to either read every file upfront or accept a double-read on a subset of files. A new API that returns the content alongside the `FilterResult` would eliminate this gap.

## Consumer: art-dupl

[art-dupl](https://github.com/LarsArtmann/art-dupl) is a Go clone-detection tool that uses gogenfilter to exclude generated files. It supports `--include-generated <category>` flags (sqlc, templ, protobuf, mockgen, stringer, generic, all) that override the filter for specific generated-code categories.

When `--include-generated` flags are active, art-dupl needs the file content for **two** purposes:

1. **gogenfilter's phase-2 detection** — checking generation comment markers inside the file
2. **`allowsContent(content)`** — art-dupl's own override logic that classifies a file caught by `FilterGeneric` into a specific category (sqlc/templ/protobuf) to decide if the user's `--include-generated` flag should rescue it

The override logic (`cmd/util.go`) checks whether a file caught by the generic "Code generated by" catch-all belongs to a category the user explicitly asked to include:

```go
// art-dupl cmd/util.go (simplified)
func shouldIncludeFile(f *gogenfilter.Filter, path string, includes generatorIncludes) bool {
    content, _ := os.ReadFile(path)                        // reads EVERY file upfront
    result, _ := f.FilterDetailedWithContent(path, content) // passes content to gogenfilter

    if result.Filtered && result.Reason == gogenfilter.ReasonGeneric &&
        includes.allowsContent(content) {                   // reuses content for override check
        return true
    }

    return !result.Filtered
}
```

## The Problem

art-dupl reads content upfront for **every file** when `--include-generated` is active, even though the filename-based filter (phase 1) would catch 5-10% of generated files without ever needing the content.

### Why Current APIs Don't Solve This

gogenfilter provides two detection APIs, but neither does both lazy reading AND content return:

| API | Lazy read? | Returns content? | Problem for art-dupl |
|-----|-----------|------------------|----------------------|
| `FilterDetailed(path)` | Yes — phase 1 filename, phase 2 content only if needed | **No** — content read internally then discarded | art-dupl must re-read files caught by `ReasonGeneric` for `allowsContent` (double-read) |
| `FilterDetailedWithContent(path, content)` | No — caller must provide content upfront | N/A — caller already has it | art-dupl reads every file upfront, including files that phase 1 would catch by filename alone (wasted read) |

### Internal Flow (Why the Gap Exists)

`FilterDetailed(path)` internally calls `detectReasonFSWithTrace` (`detection.go:634`), which already does lazy reading:

```
1. getFilenameBasedReasonWithTrace(filePath, options)     — phase 1, zero I/O
2. If phase 1 doesn't match AND needsContentCheck(options):
   a. content, err := readFile(fsys, filePath)            — reads file from disk
   b. getContentBasedReasonWithTrace(filePath, content)   — phase 2, uses content
3. Return FilterResult                                     — content DISCARDED
```

The content is read at step 2a but never returned to the caller. The information is right there, just not exposed.

### Quantifying the Waste

For a project with 1000 `.go` files, approximately:

| File category | % of files | Current (upfront read) | With lazy + return |
|--------------|-----------|----------------------|-------------------|
| Regular (not generated) | ~90% | 1 read (needed for phase 2) | 1 read (same) |
| Filename-caught generated (e.g., `models.go`, `_templ.go`) | ~5-10% | 1 read (**wasted** — phase 1 catches them) | 0 reads |
| Content-caught generated (generic marker only) | ~1-5% | 1 read (needed for phase 2 + override) | 1 read (returned, reused) |

The upfront-read approach wastes disk I/O on 5-10% of files that could be resolved by filename alone.

## Proposed API

```go
// FilterDetailedAndContent is like FilterDetailed but also returns the file content
// if it was read during phase-2 detection. The content is nil when:
//   - The filter is disabled
//   - The file is caught by an include/exclude pattern
//   - The file is caught by filename detection (phase 1)
//   - No enabled detector requires content checks
//
// When content is non-nil, it was read exactly once from the filter's filesystem
// and can be reused by the caller for additional checks without re-reading the file.
func (f *Filter) FilterDetailedAndContent(filePath string) (FilterResult, []byte, error)
```

### Behavior Matrix

| Scenario | Content returned | Why |
|----------|-----------------|-----|
| Filter disabled | `nil` | No detection performed |
| Include/exclude pattern match | `nil` | No content read |
| Phase 1 filename match (e.g., `models.go` → SQLC) | `nil` | Content not read (phase 1 sufficient) |
| No content-check detectors enabled | `nil` | Content not needed |
| Phase 2 content check ran (file not filtered) | `content` | Content was read, return for reuse |
| Phase 2 content check ran (file filtered) | `content` | Content was read, return for reuse |

### Implementation Sketch

The implementation is a thin variant of the existing `detectReasonFSWithTrace` (`detection.go:634`) that returns the content alongside the result:

```go
func (f *Filter) FilterDetailedAndContent(filePath string) (FilterResult, []byte, error) {
    if !f.IsEnabled() {
        return FilterResult{Filtered: false, Reason: "", Path: filePath, Trace: ""}, nil, nil
    }

    if len(f.includePatterns) > 0 && !f.matchesAnyPattern(filePath, f.includePatterns) {
        return FilterResult{
            Filtered: true, Reason: ReasonOutsideScope,
            Path: filePath, Trace: "excluded by include pattern scope",
        }, nil, nil
    }

    if f.matchesAnyPattern(filePath, f.excludePatterns) {
        return FilterResult{
            Filtered: true, Reason: ReasonExcludePattern,
            Path: filePath, Trace: "matched exclude pattern",
        }, nil, nil
    }

    // Phase 1: filename check (zero I/O)
    reason, trace := getFilenameBasedReasonWithTrace(filePath, f.options)
    if reason != ReasonNotFiltered {
        return FilterResult{Filtered: true, Reason: reason, Path: filePath, Trace: trace}, nil, nil
    }

    // Phase 2: content check (only if needed)
    if !needsContentCheck(f.options) {
        return FilterResult{Filtered: false, Reason: ReasonNotFiltered, Path: filePath, Trace: ""}, nil, nil
    }

    content, err := readFile(f.fsys, filePath)
    if err != nil {
        return FilterResult{
            Filtered: false, Reason: ReasonNotFiltered, Path: filePath, Trace: "",
        }, nil, fmt.Errorf("read file %q: %w", filePath, err)
    }

    reason, trace = getContentBasedReasonWithTrace(filePath, string(content), f.options)
    if reason != ReasonNotFiltered {
        return FilterResult{Filtered: true, Reason: reason, Path: filePath, Trace: trace}, content, nil
    }

    return FilterResult{Filtered: false, Reason: ReasonNotFiltered, Path: filePath, Trace: ""}, content, nil
}
```

### How art-dupl Would Use It

```go
func shouldIncludeFile(f *gogenfilter.Filter, path string, includes generatorIncludes) bool {
    result, content, err := f.FilterDetailedAndContent(path)
    if err != nil {
        return true
    }

    if result.Filtered && result.Reason == gogenfilter.ReasonGeneric &&
        includes.allowsContent(content) {
        return true
    }

    return !result.Filtered
}
```

No upfront read. No double-read. Content is read at most once, only when phase 2 is needed, and returned for reuse.

## Alternative: Workaround Without API Change

art-dupl could partially solve this today by using `FilterDetailed(path)` and conditionally re-reading only when `result.Reason == ReasonGeneric`:

```go
func shouldIncludeFile(f *gogenfilter.Filter, path string, includes generatorIncludes) bool {
    result, err := f.FilterDetailed(path)  // lazy: reads content internally if needed
    if err != nil {
        return true
    }

    if result.Filtered && result.Reason == gogenfilter.ReasonGeneric {
        content, err := os.ReadFile(path)   // re-read: double-read on ~1-5% of files
        if err != nil {
            return true
        }
        if includes.allowsContent(content) {
            return true
        }
    }

    return !result.Filtered
}
```

### Why This Is Suboptimal

| Approach | Regular files (90%) | Filename-caught (5-10%) | Generic-caught (1-5%) | Total reads (1000 files) |
|----------|--------------------|-----------------------|----------------------|------------------------|
| Current (upfront read) | 1 read | 1 read (**wasted**) | 1 read | ~1000 |
| Workaround (`FilterDetailed` + re-read) | 1 read | 0 reads | **2 reads** (double-read) | ~920 |
| Proposed API | 1 read | 0 reads | 1 read | ~910 |

The workaround is better than the current approach (eliminates wasted reads on filename-caught files) but still double-reads generic-caught files because `FilterDetailed` discards the content it read internally.

The proposed API is strictly optimal: every file is read at most once, and only when content detection is actually needed.

## Impact Assessment

### Breaking Changes

None. This is a purely additive API. Existing methods (`FilterDetailed`, `FilterDetailedWithContent`, `Filter`, `FilterWithContent`) are unchanged.

### Testing

- Existing tests unaffected (no API changes to existing methods)
- New tests needed for `FilterDetailedAndContent`:
  - Returns `nil` content when filter is disabled
  - Returns `nil` content when include/exclude pattern matches
  - Returns `nil` content when phase 1 (filename) matches
  - Returns non-nil content when phase 2 runs (file not filtered)
  - Returns non-nil content when phase 2 runs (file filtered by content)
  - Returns error when file cannot be read
  - Content matches what `os.ReadFile` would return

### Documentation

- Add to `filter.go` doc comments
- Add example to `example_test.go`
- Update `website/src/content/docs/api-reference.mdx` if it lists Filter methods

### Version

This is an additive API change. A minor version bump (e.g., v3.4.0 or v3.5.0 depending on what else is in the release) is appropriate.
