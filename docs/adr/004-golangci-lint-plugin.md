# ADR 004: golangci-lint Module Plugin Architecture

**Date:** 2026-08-10
**Status:** Accepted

## Context

Gogenfilter is a library for detecting auto-generated Go files. The primary consumer use case is linters and static analysis tools that need to skip generated code. The most popular Go linter, golangci-lint, has limited generated-file detection: it relies on filename conventions and the generic `// Code generated ... DO NOT EDIT.` comment pattern. This misses:

- Generated files with non-standard names (e.g., a sqlc file named `repository.go` instead of `models.go`)
- Generator-specific detection (distinguishing sqlc from templ from protobuf)
- Config-aware detection (knowing that `models.go` in a sqlc output dir is generated even without a header comment)

Golangci-lint v2 introduced [module plugins](https://golangci-lint.run/plugins/module-plugins/) that allow custom linters to be compiled into a custom golangci-lint binary. This is the natural distribution channel for gogenfilter's detection capabilities.

## Decision

Implement the golangci-lint plugin as a **separate Go module** in the `plugin/` subdirectory of the same repository.

### Module structure

```
gogenfilter/
├── go.mod                    # github.com/LarsArtmann/gogenfilter/v3 (main library)
├── filter.go
├── detection.go
├── ...
└── plugin/
    ├── go.mod                # github.com/LarsArtmann/gogenfilter/plugin (separate module)
    ├── plugin.go             # register.LinterPlugin implementation
    ├── plugin_test.go
    ├── .custom-gcl.yml       # example build config
    ├── .golangci.example.yml # example runtime config
    └── README.md
```

### Why a separate module?

1. **Dependency isolation**: The plugin requires `github.com/golangci/plugin-module-register` and `golang.org/x/tools/go/analysis`. These are heavy dependencies that should NOT be pulled into the main library. Library consumers (e.g., art-dupl, golangci-lint-auto-configure) should not transitively depend on golangci-lint's plugin SDK.

2. **Independent versioning**: The plugin can be versioned independently from the library. Breaking changes in golangci-lint's plugin API should not force a major version bump in the library.

3. **Standard pattern**: This follows the convention used by other golangci-lint plugins (e.g., `github.com/golangci/example-plugin-module-linter`).

### Plugin design

- **Interface**: Implements `register.LinterPlugin` with `BuildAnalyzers()` and `GetLoadMode()`.
- **Load mode**: `LoadModeSyntax` — the plugin only needs AST comments and filenames, not type information. This is faster than `LoadModeTypesInfo`.
- **Detection**: Creates a `gogenfilter.Filter` in `BuildAnalyzers()` (once per linter initialization, not per package). The `run()` function converts absolute file paths from `pass.Fset` to relative paths and calls `FilterDetailed()`.
- **Diagnostic**: Reports one diagnostic per detected generated file: `"file is auto-generated by <generator> — consider excluding from linting"`.
- **Configuration**: Supports `generators` (restrict to specific generators) and `exclude-paths` (glob patterns to skip).

### What the plugin does NOT do

- **Auto-exclude**: The plugin reports diagnostics; it does not automatically suppress other linters' diagnostics for generated files. Users configure `issues.exclude-rules` in `.golangci.yml` for that.
- **Custom detectors**: The initial version does not expose a `RegisterDetector()` API. This is planned for a future iteration.

## Consequences

- The `plugin/` module has its own `go.mod` with a `replace` directive for local development (`replace github.com/LarsArtmann/gogenfilter/v3 => ../`). The replace directive must be removed before publishing.
- The plugin needs its own CI pipeline (or CI job) to verify it compiles and tests pass with the latest gogenfilter and golangci-lint versions.
- Users build a custom golangci-lint binary using `golangci-lint custom -v` with a `.custom-gcl.yml` file.
- The `go.work` file needs to include the plugin module for local development.
