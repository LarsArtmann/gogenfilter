## d) TOTALLY FUCKED UP

### 1. Left the `replace` directive in plugin/go.mod
The plugin's `go.mod` has `replace github.com/LarsArtmann/gogenfilter/v3 => ../` for local development. This MUST be removed before publishing. It's documented in ADR 004 and TODO_LIST.md, but it's a footgun — if someone tries to `go get` the plugin module right now, the replace directive will cause issues (though Go ignores replace directives from imported modules, so it's actually harmless for consumers — but it should still be removed before tagging).

### 2. Plugin go.mod version is v3.5.0 — which isn't tagged yet
The plugin requires `github.com/LarsArtmann/gogenfilter/v3 v3.5.0`, but v3.5.0 hasn't been tagged. This works locally because of the `replace` directive, but if someone removes the replace and tries to build, `go mod tidy` will fail because v3.5.0 doesn't exist on the proxy yet. The plugin cannot be published until v3.5.0 is tagged.

### 3. analysistest approach was wrong
I spent 3 round trips trying to get `analysistest.Run` working with file-level diagnostics. The `// want` comment marker pattern expects diagnostics at specific positions, but my analyzer reports at `file.Pos()` (the package keyword). The first test data file imported `github.com/a-h/templ` which broke the test compiler. I should have either:
- Used simpler test data files with no external imports from the start
- Used a mock `*analysis.Pass` instead of `analysistest`
- Recognized that file-level diagnostics don't fit `analysistest`'s model well

### Technical

6. **Plugin does not handle the `pass.Pkg` path correctly for module-rooted projects** — The `run()` function uses `os.Getwd()` to compute relative paths. This works when golangci-lint is run from the project root, but may produce wrong results in monorepo or workspace setups. Should use `pass.Pkg.Path()` or the module root from `pass.Fset`.

7. **Plugin creates the Filter in `BuildAnalyzers()` but the `FS` is not set** — The filter uses the default `os.DirFS(".")`. This is correct for the plugin's use case (golangci-lint runs from the project root), but it means the filter's config-aware SQLC detection will walk the real filesystem. This is the intended behavior, but it's worth documenting.

8. **No CI job for the plugin module** — The `plugin/` directory has its own `go.mod` but CI only runs `go test ./...` on the root module. Need a separate CI job or workspace setup.

9. **`go.work` includes plugin but `nix flake check` doesn't test it** — The Nix flake only checks the root module. The plugin module is invisible to Nix quality gates.

10. **Website sidebar has "Filter" before "Detection"** — This may be the wrong order; "Detection" was there first and covers the core concept. Consider reordering or grouping differently.
